## 6. Other gaps and inconsistencies found (evidence, not opinion)

1. **~50 of the 92 closure plugins have no lze spec and cannot load.** Verified by (a) grepping the new Lua tree for each plugin name and (b) the runtime probe, where only 22 pack dirs were on `runtimepath`. Unreferenced: `cornelis`, `crates.nvim`, `haskell-vim`, `helm-ls.nvim`, `kulala.nvim`, `lazydev.nvim`, `litee.nvim`, `neotest`, `neotest-golang`, `neotest-python`, `neotest-testthat`, `nvim-dap-go`, `nvim-dap-python`, `nvim-dap-ui`, `nvim-dap-virtual-text`, `nvim-jdtls`, `nvim-lint`, `nvim-treesitter-context`, `render-markdown.nvim`, `rustaceanvim`, `SchemaStore.nvim`, `unimpaired.nvim`, `venv-selector.nvim`, `vim-dadbod`, `vim-dadbod-completion`, `vim-dadbod-ui`, `vim-illuminate`, `vim-startuptime`, `vimtex`, `yazi.nvim`, `copilot-lualine`, `friendly-snippets`.
2. **`friendly-snippets` is orphaned** — installed as an opt plugin (`_plugins.nix` `blink` group), no lze spec, not on rtp at runtime. blink's `snippets` source is configured but has no snippet collection to read.
3. **`yazi.nvim` is installed and never loadable**, while `_plugins.nix`'s own closing comment says "mikavilpas/yazi.nvim — oil is the file manager … Not installed here". The `files` group's `data` list does include `yazi-nvim`. Same class of drift: the tail comment claims `nvim-dap-ui` and `persistence.nvim` are "not installed", but `nvim-dap-ui` is in the closure (dep of `nvim-dap-view` and also explicitly listed in the `dap` group's `data`).
4. **`vim-illuminate` and `unimpaired.nvim` are installed with no old-config provenance** (old config had both commented out) and no spec → closure weight with zero behaviour.
5. `_plugins.nix`'s `lsp` note in `modules/editors/lsp.nix` ("Everything here is currently provided by mason", "lsp module enabled via hmAspects") describes the _old_ situation; the wrapper now supplies `lua-language-server`, `stylua`, `bash-language-server`, `shellcheck`, `vscode-langservers-extracted` itself (runtimePkgs) and the rest arrive from the home profile. `dockerfile-language-server` and `docker-compose-language-service` are listed in `modules/editors/lsp.nix` but are **not** on PATH today.
6. No `build`/installer step exists for `markdown-preview.nvim` or the treesitter grammars in the new closure — grammars come from `withPlugins`, but the old config's `disable` list (`latex text opencode fstab kdl`) is only partially reproduced as a FileType autocmd; a live treesitter check was not run.
7. `_keymap-parity.md` already tracks the keymap backlog with `DONE` markers; section 5 here shows 97 of the old 256 source-declared maps exist (38%), with 161 still open. Its `<leader>dpp`/`<leader>cf` "DONE" annotations are accurate against the sources.

## Recommended next step (single highest-value action)

Restore the LSP layer first: (1) add `vim.lsp.enable` lines for the servers whose binaries are already on PATH (`jsonls`, `yamlls`, `marksman`, `texlab`, `gopls`, `helm_ls`, `eslint`) and (2) re-add LazyVim's `servers["*"]` capabilities + `LspAttach` keymaps + `vim.diagnostic.config`, because that restores ~20 `<leader>c`/`g` maps and all diagnostics UX in one file. Everything else in Tables 1–5 is either a spec addition or a parked decision.
