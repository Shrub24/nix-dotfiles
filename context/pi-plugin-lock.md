# Pi plugin lock

## Compiled plugins resolve through one npm lock that extends Pi's own

**Id:** 7d1f4a02-cd63-4a5f-9f4a-9c6c1b0e5a71
**Type:** decision
**Status:** active
**Evidence:** confirmed
**Source:** the generated `pkgs/pi-plugins/plugins.lock.json`, the six member manifests it was built from, and Pi-Bolt's `nix/pi-bolt.nix` at the pinned revision
**Verification:** corroborated — the lock resolves `@narumitw/pi-tui-kit` to 0.59.0 and `web-tree-sitter` to 0.26.13, the two versions the plugins' own ranges allow; `zod` nests under the one plugin that needs a major Pi does not carry; the payload evaluates with the lock and builds with it
**Revisit when:** Pi-Bolt changes the lock's shape again (it is Pi's lock with plugin workspaces added), or a plugin needs a closure the lock cannot express (a bun or pnpm lock source keeps `nodeModules`)

A compiled plugin's npm dependencies used to come from a hand-maintained
`libraries` map in `pkgs/pi-plugins/default.nix`, merged into one tree and
copied into every plugin's `node_modules`. Nothing tied an entry to the plugin
that imported it, so a pin could drift from the `package.json` beside the
import, and the only detection was a bundler error naming a specifier — the
`pi-radar@0.2.0` incident recorded in
[pi-plugin-dependencies.md](pi-plugin-dependencies.md).

**Decision.** The plugin set resolves through one npm lock,
`pkgs/pi-plugins/plugins.lock.json`, generated by
`nix run .#update-plugin-lock` and passed to the payload as `pluginLock`. The
lock is Pi-Bolt's own release lock with each plugin added as an npm workspace,
which gives the properties that matter:

- Pi's entries are the release's, unchanged, so the executable's dependency set
  is the one its authors tested;
- a plugin that needs a version Pi does not carry gets it nested under its own
  folder, so no plugin has to lose a range to another;
- everything shared is bundled once.

Only plugins that declare dependencies are members: `ask-user-question`,
`herdsman`, `otel`, `permission-system`, `todo`, `tool`. A plugin without
declared dependencies needs no closure at all, and one that gains a dependency
and is missing from the member list fails the compile's dependency check, which
names it.

**Reason.** A range belongs next to the import that needs it, and the resolver
must be the one the ecosystem uses. Deriving the closure from each plugin's own
`package.json` removes both halves of the old failure: the pin cannot be written
down twice, and a mismatch is reported by the lock generator, which has the
network, instead of by a bundler that only knows a specifier.

**Rejected alternative:** one merged lock for Pi-Bolt's dependencies and the
plugins' together, so a single tree serves the whole build. It preserves Pi's
pins only if every one of them is re-pinned by hand as an npm `override`, and it
moves Pi-Bolt's own resolution into this repository — a derivation that
currently rebuilds only when the release changes would rebuild on every plugin
pin move. Nesting per plugin reaches the same single-copy outcome without owning
Pi's resolution.

**Rejected alternative:** keeping `nodeModules` and adding only the build-time
range check. The check catches a wrong pin but not a plugin importing a library
it never declared, and the shared tree still stages a copy of packages Pi
already provides.

**Consequence.** The lock carries Pi's entries, so it is stale after every
Pi-Bolt input bump, and evaluation refuses it by name (`pluginLock is stale`)
until `nix run .#update-plugin-lock` runs again. That regeneration belongs to the
same step as the bump. `bash-processes` stays out of the lock: its one
dependency is the sibling `tool-renderer`, declared `workspace:*` — a pnpm and
bun specifier npm rejects — and the recipe's own `dependencies` edge links it
into that plugin's `node_modules` instead.
